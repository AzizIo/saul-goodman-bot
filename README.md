## Общая информация

**Название:** Saul Goodman  
**Тип:** приватный Telegram-бот для работы с eSIM  
**Визуальный стиль:** эстетика Saul Goodman / Better Call Saul — дерзкий, уверенный тон, выразительные сообщения и эмодзи.

Бот должен предоставлять пользователям закрытый кабинет, в котором они могут отправлять QR/eSIM на проверку, отслеживать состояние заказов, видеть заработок и запрашивать выплаты. Администратор модерирует пользователей и заказы, управляет операторами, выплатами и обращениями в поддержку.

## 1. Стек и окружение

- Python 3.10+
- aiogram 3.x
- SQLite через стандартный модуль `sqlite3`
- Ubuntu Server
- systemd для запуска и автоматического перезапуска бота
- HTML-разметка Telegram для сообщений

## 2. Структура базы данных (SQLite)

### Таблица `users`

| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER PRIMARY KEY | Telegram ID пользователя |
| `balance` | REAL | Общий баланс |
| `available` | REAL | Сумма, доступная к выводу |
| `reg_date` | TEXT | Дата регистрации |
| `status` | TEXT | Статус: `pending`, `active`, `banned` |

Статусы пользователя:

- `pending` — ожидает одобрения администратора.
- `active` — доступ одобрен.
- `banned` — доступ заблокирован.

### Таблица `orders`

| Поле | Тип | Описание |
|---|---|---|
| `id` | INTEGER PRIMARY KEY AUTOINCREMENT | ID заказа |
| `user_id` | INTEGER | Telegram ID пользователя |
| `operator` | TEXT | Оператор |
| `price` | REAL | Стоимость/начисление по заказу |
| `phone` | TEXT | Номер телефона из подписи к QR |
| `status` | TEXT | Статус заказа |
| `fail_reason` | TEXT | Причина отклонения |
| `date` | TEXT | Дата создания |

Статусы заказа:

- `pending` — ожидает проверки.
- `in_progress` — взят в работу.
- `success` — успешно засчитан.
- `failed` — отклонён.

## 3. Конфигурация (`config.py`)

В конфигурации должны быть предусмотрены:

- `BOT_TOKEN` — токен Telegram-бота.
- `ADMIN_ID` — Telegram ID администратора.
- `CHANNEL_ID` — ID канала для проверки подписки.
- Ссылка на канал для кнопки вступления.
- `OPERATORS` — словарь операторов: название, цена, флаг `open` (приём включён/выключен).
- `RANKS` — уровни пользователя: название, порог успешных сдач, бонус к цене.

Секреты и персональные значения должны загружаться из файла `.env` и не попадать в Git.

## 4. Доступ и приватность

Обработка команды `/start`:

1. Проверить подписку пользователя на канал.
2. Если пользователь не подписан — показать кнопки **«Вступить»** и **«Проверить»**.
3. Если подписан, но отсутствует в БД — создать пользователя со статусом `pending`.
4. Отправить администратору уведомление о новой заявке с командой `/approve_ID`.
5. Если статус `pending` — показать сообщение об ожидании одобрения.
6. Если статус `banned` — отказать в доступе.
7. Если статус `active` — показать главное меню.

## 5. Главное меню

Главное меню реализовать через Reply-клавиатуру:

- ⚖️ Начать сделку
- 💼 Профиль
- 📊 Статистика
- 🆘 Поддержка
- ⚙️ Админ-панель — отображается только для `ADMIN_ID`.

## 6. Приёмка QR/eSIM (сдача)

1. После нажатия **«⚖️ Начать сделку»** показать Inline-меню операторов в две колонки.
2. У каждого оператора отображать индикатор доступности:
   - 🟢 — приём открыт.
   - 🔴 — приём закрыт.
3. После выбора открытого оператора запросить фото QR/eSIM.
4. Номер телефона обязателен и должен быть указан в подписи к фотографии.
5. Если номер не указан — сообщить об ошибке и запросить корректную отправку.
6. Если данные корректны — создать заказ со статусом `pending`.
7. Пользователю отправить подтверждение: **«Принято, заказ #X, сумма $Y»**.
8. Администратору в личные сообщения отправить фото и сведения:
   - ID пользователя;
   - оператор;
   - номер телефона;
   - ID заказа.

Команды администратора для обработки заказа:

- `/ok_ID` — засчитать заказ.
- `/progress_ID` — взять заказ в работу.
- `/no_ID` — отклонить заказ с обязательным указанием причины.

## 7. Профиль пользователя

Профиль должен быть оформлен как компактный HTML-дашборд с эмодзи.

Пример карточки:

```html
📥 <b>Кабинет продавца</b>

✦ <b>Сводка</b>

✅ Встало: {success_count}
⏳ В работе: {in_progress_count}
⛔ Брак: {failed_count}
📥 Загружено: {total_count}
💵 За вставшие: ${earned_money}

✦ <b>Операторы</b>

{op_name}: ✅ {s} ⏳ {p} ⛔ {f}

✦ <b>До следующего ранга:</b>

{progress_bar}

До {rank_name} осталось {x} сдач.
```

Требования к прогресс-бару:

- 10 квадратов.
- 🟩 — заполненная часть.
- ⬜ — незаполненная часть.
- Расчёт заполнения: `(success_count / rank_next_threshold) * 10`.

В профиле должна находиться Inline-кнопка **«💳 Вывести»**.

## 8. Статистика

Отдельная кнопка **«📊 Статистика»** должна показывать:

- Количество сданных заказов за последние 24 часа (SQL-фильтр по дате).
- Детальную статистику по каждому оператору: успешно, в работе, брак.
- Общее количество брака.
- Причины брака, если администратор указал их при отклонении.

## 9. Вывод средств (выплаты)

1. В профиле пользователь нажимает Inline-кнопку **«💳 Вывести»**.
2. Бот запрашивает адрес кошелька:
   - USDT BEP20;
   - USDT TRC20.
3. Пользователь отправляет адрес текстом.
4. Бот создаёт заявку и отправляет администратору уведомление с:
   - ID пользователя;
   - суммой заявки;
   - адресом кошелька;
   - ID заявки.
5. Администратор вручную выполняет перевод.
6. Администратор отправляет чек пользователю через команду `/reply_ID`.
7. Администратор подтверждает списание командой `/yes_ID`.
8. После подтверждения сумма заявки списывается с доступного баланса пользователя.

## 10. Поддержка (тикеты)

1. Пользователь нажимает **«🆘 Поддержка»**.
2. Бот предлагает написать сообщение.
3. Обращение пересылается администратору в личные сообщения с ID пользователя и командой `/reply_ID`.
4. Администратор отправляет ответ через сценарий `/reply_ID`.
5. Ответ доставляется пользователю.

## 11. Админ-панель

Админ-панель доступна только пользователю с `ADMIN_ID`.

Функции:

- Список пользователей: `SELECT id, status, balance FROM users`.
- Вывод списка пользователей в HTML.
- Управление операторами через Inline-кнопки.
- Открытие и закрытие приёма по каждому оператору.
- Изменения состояния операторов должны сохраняться в БД либо в конфигурационном хранилище и переживать перезапуск бота.

## 12. Критические технические требования

### 12.1. Обновление сообщений

Не допускать ошибок Telegram вида `message is not modified`.

При обновлении сообщений (например, при переключении статусов операторов) использовать один из подходов:

- Проверять, изменился ли текст/разметка, прежде чем редактировать сообщение.
- Удалять старое сообщение через `call.message.delete()` и отправлять новое через `call.message.answer()`.

### 12.2. FSM (состояния)

Состояния должны быть чётко разделены:

- `waiting_for_qr`
- `waiting_for_withdraw_wallet`
- `waiting_for_support_msg`
- `waiting_for_admin_reply`

После завершения каждого сценария обязательно вызывать `state.clear()`.

### 12.3. Файловая структура

В исходном ТЗ предусмотрены:

- `main.py` — основной код бота.
- `config.py` — конфигурация.
- `.env` — токен и ID.

Секретный файл `.env` не коммитить. В репозитории хранить только безопасный шаблон `.env.example`.

### 12.4. Ограничение админ-команд

Все административные команды:

- `/ok`
- `/no`
- `/progress`
- `/reply`
- `/approve`
- `/ban`

должны обрабатываться **только в личном чате администратора**. В группах и супергруппах эти команды должны игнорироваться.

## 14. Дополнительные требования к надёжности и безопасности

Эти требования дополняют исходное ТЗ и должны учитываться при реализации:

- **Денежная точность:** не использовать двоичную арифметику `REAL` для финансовых расчётов в новой реализации. Предпочтительно хранить суммы в целых минимальных единицах (например, центы) или использовать `Decimal` с корректным преобразованием на границе БД.
- **История операций:** предусмотреть журнал начислений, списаний и выплат. Баланс должен быть объясним через историю транзакций.
- **Идемпотентность:** повторное нажатие кнопки или повторная команда администратора не должны повторно начислять деньги, менять завершённый заказ или списывать выплату.
- **Атомарность:** изменение статуса заказа и соответствующая финансовая операция должны выполняться в одной транзакции SQLite.
- **Выплаты:** фиксировать сумму заявки при её создании; подтверждать только конкретную заявку и списывать именно зарезервированную/подтверждённую сумму, а не весь баланс пользователя.
- **Валидация:** проверять формат номера телефона, подпись к фото, адрес кошелька, сумму и допустимость перехода между статусами.
- **Доступ:** проверять Telegram ID администратора на каждом административном обработчике, а не только скрывать кнопку админ-панели.
- **Файлы QR/eSIM:** QR и данные активации могут содержать секреты. Ограничить доступ к ним, не публиковать их в логах, определить срок хранения и удалять файлы после завершения установленного срока. Обрабатывать такие данные только при наличии разрешения владельца и в рамках правил соответствующего оператора.
- **Секреты:** не хранить токен бота, ключи и реальные ID в исходном коде. Добавить `.env` в `.gitignore`.
- **SQLite:** включить внешние ключи, использовать параметризованные SQL-запросы, настроить разумные таймауты и резервное копирование.
- **Ошибки и логи:** логировать технические ошибки и важные действия без записи токенов, адресов кошельков и содержимого QR.
- **Тестирование:** покрыть тестами регистрацию, доступ, FSM-сценарии, переходы статусов, начисления, выплаты, ограничения админа и повторную обработку событий.

## 15. Развёртывание

Целевое окружение — Ubuntu Server.

Требования к запуску:

- Отдельное виртуальное окружение Python.
- Установка зависимостей из `requirements.txt`.
- Настройка переменных окружения через защищённый `.env` или systemd EnvironmentFile.
- Запуск через systemd.
- Автоматический перезапуск при сбое.
- Просмотр логов через `journalctl`.
- Регулярное резервное копирование SQLite-базы.
- Проверка прав доступа к каталогу базы данных и загружаемым файлам.

## Критерии готовности

Проект можно считать готовым к первому релизу, когда:

- [ ] Пользователь проходит проверку подписки и модерацию.
- [ ] Активный пользователь может отправить QR/eSIM с номером телефона.
- [ ] Администратор может взять заказ в работу, засчитать или отклонить его.
- [ ] Профиль корректно показывает заказы, заработок и ранг.
- [ ] Статистика корректно считает данные за 24 часа и по операторам.
- [ ] Пользователь может создать заявку на выплату.
- [ ] Администратор может обработать выплату без повторного списания.
- [ ] Поддержка позволяет отправлять обращения и ответы.
- [ ] Админ-панель и все административные команды защищены.
- [ ] Повторные действия не приводят к повторному начислению или списанию.
- [ ] Ключевые сценарии покрыты тестами.
- [ ] Бот стабильно запускается и работает под systemd на Ubuntu.

**Документ является основной спецификацией проекта.** Изменения требований и принятые архитектурные решения следует фиксировать в репозитории.
