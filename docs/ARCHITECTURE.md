# Архитектурные решения Saul Goodman ⚖️

Документ фиксирует решения, принятые при реализации ТЗ (README.md).
Спецификация остаётся главным документом; здесь — как именно она выполнена.

## 1. Деньги в целых центах

`REAL` для финансов исключён. Все суммы — `INTEGER` центов.
Граница преобразования — `config.to_cents()` / `texts.money()`.
В БД нет ни одного `REAL`-поля, связанного с балансом.

## 2. Журнал транзакций

Таблица `transactions` объясняет баланс: `SUM(amount) = users.balance`.

- `earning` — начисление за засчитанный заказ;
- `withdraw_paid` — фактическое списание при подтверждении выплаты;
- `adjust` — ручные корректировки (зарезервировано).

Резервирование (`available -= amount`) и его возврат при отказе **не**
пишутся в журнал: общий баланс при этом не меняется, а запись ломала бы
инвариант «сумма проводок = баланс». Эти события отражает статус заявки
в `withdrawals`. 

Уникальный частичный индекс
`(user_id, kind, ref_type, ref_id)` делает повторное начисление по одному
заказу физически невозможным.

## 3. Идемпотентность и атомарность

Каждый переход статуса — условный `UPDATE ... WHERE status IN (...)`
внутри `BEGIN IMMEDIATE`. Если строк не затронуто, значит переход уже
совершён: обработчик отвечает «уже завершено» и ничего не начисляет.

| Действие | Защита |
|---|---|
| `/ok_ID` повторно | `UPDATE ... WHERE status IN (pending, in_progress)` |
| `/no_ID` повторно | то же + не трогает `success` |
| `/progress_ID` повторно | допустим, статус уже `in_progress` |
| `/yes_ID` повторно | `WHERE status = 'pending'` в `withdrawals` |
| `/reject_ID` после `/yes_ID` | невозможно: статус уже `paid` |
| Повторный `<callback>` | правка сообщения идемпотентна |

## 4. Выплаты

Заявка фиксирует сумму в момент создания и резервирует её
(`available -= amount`). Подтверждение списывает **именно эту сумму**
из `balance`, а не «весь доступный остаток». Отклонение возвращает резерв
в `available`. Повторные команды не списывают и не возвращают дважды.

## 5. Доступ

`IsAdmin` проверяет `ADMIN_ID` **и** `chat.type == "private"` на каждом
админ-обработчике, а не только прячет кнопку. В группах админ-команды
не обрабатываются. `ADMIN_ID = 0` означает «админ не настроен».

## 6. FSM

`Deal.waiting_for_qr`, `Withdraw.waiting_for_withdraw_wallet`,
`Support.waiting_for_support_msg`, `Admin.waiting_for_admin_reply`,
`Admin.waiting_for_fail_reason`.
Каждый сценарий завершается `state.clear()`, включая отмену и ошибочные ветки.

## 7. «message is not modified»

`services.safe_edit()` сверяет текст, ловит `TelegramBadRequest`
с `message is not modified` и молча выходит. Переключение операторов в
админке и обновление профиля используют его.

## 8. QR/eSIM

По умолчанию файлы не сохраняются: бот пересылает админу `file_id`.
`cleanup_old_orders()` ежесуточно обнуляет `file_id` старше
`QR_RETENTION_DAYS`. Логи не содержат ни номеров, ни адресов кошельков,
ни содержимого QR.

## 9. Структура

Требование ТЗ о `main.py` и `config.py` в корне соблюдено; код разнесён
по пакету `bot/` (db, texts, keyboards, states, filters, validators,
services, handlers/*), что даёт тестируемость без поднятия бота.

## 10. Известные компромиссы

- FSM-хранилище — `MemoryStorage`: состояния теряются при перезапуске.
  Для сценариев, где это важно, данные дублируются в БД (заказы, тикеты,
  заявки создаются сразу, а не «по факту ответа»).
- Ранги берутся из `config.RANKS` и применяются при засчитывании заказа.
- Проверка подписки при недоступном канале (бот не админ) не блокирует
  вход — иначе пользователи застряли бы в бесконечной проверке. Причина
  пишется в лог.
